Module 05 · Week 2: Choose metrics with consequences

BrewByte assignment: Extend Module 4 into an imbalanced escalation classifier. Deliberately add a post-outcome leakage feature, expose misleading performance, remove it, and rebuild the evaluation. Compare rule-based, dummy, and trained approaches.

Learn the concept

Precision asks how many flagged cases were correct; recall asks how many true cases were found. F1 balances them, while a confusion matrix shows actual counts. Accuracy can hide poor minority-class performance. Regression uses different measures such as MAE and RMSE. Select metrics based on consequences before examining the test score.

Worked business example

If only five of one hundred requests are urgent, predicting never urgent is 95 percent accurate but finds no urgent requests. Missing a safety issue has a different cost from reviewing an extra routine ticket.

Guided practice

Read this week's assigned resource sections about Confusion matrices, precision/recall/F1, PR tradeoffs, MAE/RMSE. Spend about three hours on reading, small examples, and explaining the vocabulary in your own words. You are not expected to complete every linked course this week.

Open the guided notebook or starter script. The notebook names the dependency and execution requirements. Run the relevant worked example and inspect its inputs and outputs. For Module 1, begin with a manual prompt comparison; coding is introduced in Module 2.

Calculate precision, recall, and F1 from a small hand-worked confusion matrix, then verify with code. Explain the false-positive and false-negative costs for BrewByte.

Change one input or condition, predict the result, then run or observe it. Preserve a failing case before repairing it. Complete the task in your own learning repository rather than modifying the public teaching source.

Security boundary

Treat evaluation data and metric reports as integrity assets. Restrict edits, record dataset/model hashes and versions, and distinguish honest mistakes from deliberate metric manipulation. Never equate a language model's stated confidence with calibrated probability.

Submit evidence

Hand-verified metric examples and automated report. Include commands or procedure, relevant outputs, one failed case, your interpretation, and AI-assistance disclosure. Use synthetic data only. Clearly distinguish personally executed work, observed instructor demonstrations, and pending exercises.

Check your understanding

  • Which assumption in choose metrics with consequences could make your BrewByte result misleading?
  • What fails if the input is malformed, unauthorized, or missing?
  • What evidence would convince a reviewer that your change works on an unseen case?

These public questions are formative. Explain your reasoning; they are not hidden certification questions.
